# PDF documents and accessibility

## Goal

Generate PDF documents from the same templates and make accessibility a hard requirement for emails
and PDFs (WCAG 2.1 AA / EN 301 549, PDF/UA-1).

## Done

- PDF templates (`format: pdf`) with page options in the frontmatter; HTML with standard paged-media
  CSS (`@page`, header/footer in margin boxes, MJML columns outside `@media`); `.pdf.json` for the
  backend renderer; `templaitor pdf`, `compile --pdf`.
- Pluggable PDF engines (`pdf.engine`): WeasyPrint, Prince, Chromium.
- Accessibility checker (language, title, headings, alt text, links, data tables, contrast, text size)
  on every compile/preview; heading semantics in the editor; demo templates fixed to comply.
- Accessibility report aside in the preview; PDF view with engine selector and veraPDF validation.

## Decision: recommended PDF engine

Measured with veraPDF 1.30.4 (PDF/UA-1 profile) on the demo invoice:

| Engine | Result |
|---|---|
| WeasyPrint (`--pdf-variant pdf/ua-1`) | **compliant** — 106 rules passed, 0 failed |
| Chromium (`page.pdf({ tagged: true })`) | not compliant — 4 rules failed (7.1-3, 7.1-8, 7.18.1-2, 7.18.5-2) |
| Prince (`--pdf-profile=PDF/UA-1`) | not tested (installing the package was not allowed in the session) |

Since accessibility compliance is the priority, **WeasyPrint is the recommended (and default `auto`) engine**.
