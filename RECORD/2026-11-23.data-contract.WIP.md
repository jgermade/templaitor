## 2026-11-23 · contract in the frontmatter, engine, API and the Design view's Data panel

- Request: the demo data (JSON5, shown in Preview/PDF) could be shown as types in the Design view, defining
  the contract. Decisions with the user: the contract goes in the frontmatter (`data:`), translations stay in
  the `.yml` (the user first asked about an `attachments` property in the yml and what the frontmatter is;
  the conclusion: "translations in the yml, the rest in the frontmatter"); `/v1/send` rejects data that does
  not match with 422.
- `src/shared/contract.js`: `normalizeContract` (short form `name: type`, `{ type, required, description, of }`,
  an object without `type` = its fields), `validateData` (paths like `items[2].qty`; numbers accepted as
  text; URLs absolute or `/path`; extra fields allowed), `inferContract` (types from values: url/email/date
  detected; used names required), `contractToYaml`, `toJsonSchema` (2020-12), `usedVariables` (root names in
  Jinja2 tags; loop/set variables, filters, attributes, keyword arguments, string literals excluded).
- Engine: `compileSource` returns `contract`, `hasContract`, `usedVars` and warns about undeclared / unused
  fields (attachment `context` counts as a use); in design mode the used variables come from the plain
  source (the canvas HTML has chips: first version reported "not used" for everything inside texts).
  `previewDraft` checks the demo data. `compileTemplate` writes `<name>.schema.json`. `message.js`:
  `contractOf`, `checkContract` (422 + `details`), `templateSchema`; `renderMessage` / `renderPdfDocument`
  validate (option `validate: false`), after the language and format checks (so those errors come first).
- Bugs the contract exposed in attachments: (1) an attached document got only its `context` object, without
  the email's `assets_url` etc. (broken logo in real sends); (2) the document's own **demo data filled the
  gaps in real sends** (a missing field would put the demo customer on a real invoice). Now: `context`
  object + the email's top-level plain values; demo data only in editor previews (`preview` flag); the
  attached document's contract is checked when the email is rendered/enqueued.
- API: `GET /v1/schema?template=`; error bodies carry `details` when present; library `engine.schema(id)`.
- Editor: `store.contract` / `hasContract`, `setContract` (short YAML, leaf maps in flow style; frontmatter
  written with `lineWidth: 0`), `updateField` / `renameField` / `addField` / `removeField`,
  `generateContract` (keeps declared fields). `views/DataPanel.svelte` in the Design sidebar ("Data"): type
  icon, name, type select (list: "of" type, objects → nested fields), required checkbox, description, "not
  used" mark, "Used but not declared" chips that declare with one click, "Generate from demo data" / "Start
  empty" / "Complete from demo data". Inspector suggestions (variables, Show only if, Repeat for each) come
  from the contract. Icons calendar / toggle / list.
- Templates: contracts for email-verification, order-confirmation and invoice (demo and repository); my first
  version had unquoted descriptions with commas inside `{ … }` (YAML split them) — quoted.
- Checks: engine tests (contract functions; warnings; demo data; design = preview usage; 422 with details,
  also for the attached invoice; attachment data) and service test (`/v1/send` 422 with details and nothing
  queued; `/v1/schema`) — `node --test` 41/41. Chromium: Data panel; changing a type rewrites the
  frontmatter; removing `order_id` → "Used but not declared: order_id" → one click declares it; axe on the
  panel: 0 violations (after darkening the hint text: 4.39:1 → #52525b).
